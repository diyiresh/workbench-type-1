# 项目群聊接入与验收

本次范围经用户确认：群聊能直接向 Codex、Cursor、WorkBuddy 提问，由对应成员真实回复。沿用 Node.js、现有消息台账和 CLI/文件队列，不引入新的聊天系统或付费 API。

参考设计：[Mattermost 消息与机器人接入](https://github.com/mattermost/mattermost/blob/master/docs/main/integrations-guide/incoming-webhooks.mdx)，借鉴指定接收成员、消息身份与回复关联。直接迁移会引入独立账号、数据库和台账，故只复用设计。[Cursor CLI](https://cursor.com/docs/cli/overview) 提供非交互调用；当前使用已有 ask 模式与 JSON 输出。

## 使用

在项目群聊选择回复成员并发送。默认 Codex；正文支持 @Codex、@Cursor、@WorkBuddy，可同时指定多人。正文指定成员优先于选择框。仅已加入项目的成员可回复。“三位成员分别回答”需要项目包含三位成员。

普通讨论只产生回复，不改变业务阶段、不解除返工暂停、不代替正式复核或 Start Writing。成员读取项目目标、约束、阶段成果和近期对话；上下文有长度限制，不能宣称已阅读未提供的原件。需要实际查证或实施时，先说明待执行事项。明确 Start Writing 继续沿用原写作授权流程。

Codex 和 Cursor 由后台自动调用，WorkBuddy 进入同一个 data/workbuddy-queue 文件队列，沿用 scripts/workbuddy-queue.js。无需逐次转发，工作台和 WorkBuddy 必须运行。WorkBuddy 每轮仍只领取一项；已有任务占用时聊天等待。可手动运行现有领取任务加速。

## 接口与状态

POST /api/departments/runs/:runId/messages，正文 sender=chairman、text、recipient（all 默认 Codex / codex / cursor / workbuddy / everyone）、chat=true。省略 chat 保持原纯留言接口兼容，不追溯派发历史消息。

唯一台账 chatJobs 保存 queued、doing、waiting、done、failed；projectMessages 保存真实回复及 replyTo。等待领取不能当作已领取；只有实际结果收编后才显示成员回复。失败可单独重试回复，不重启整个部门。服务重启标记中断，不自动重复消费额度。不会让成员回复自动触发递归对话。

## 验收清单

- 三成员路由、重复调度不重复调用，回复关联原问题。
- 暂停项目可以讨论，业务阶段和写作授权不被讨论修改。
- WorkBuddy 群聊任务无需部门执行项领取，使用相同队列和结果校验。
- 返回空文本、未登录、超时、重启等均显示真实失败。
- 输入框草稿、成员选择、中文输入和滚动位置保留。
- Codex / Cursor 真实调用独立验收；WorkBuddy 实际桌面领取与回复以真实回执为准，契约测试不等同于桌面运行验收。
