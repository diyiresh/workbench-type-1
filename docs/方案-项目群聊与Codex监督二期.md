# 项目群聊与 Codex 监督二期开发方案

版本：0.1  
日期：2026年10月9日  
依据：`工作台搭建.mp4`、当前工作台 v0.8.0、现有虚拟部门与 Codex 一期实现。

## 1. 目标

把工作台从“阶段流程看板”升级为“用户提交目标后，由 Codex 统筹、Cursor 执行、WorkBuddy 提议、Ollama 汇总的项目部门”。用户只负责目标、保密边界和关键不可逆决定；日常拆解、派工、回执、讨论、追问、验收和返工由工作台与 Codex 完成。

本方案吸收视频中的四个有效思想：项目协议、共享文件、任务日志、成员分工。视频中的视觉风格不是本方案的功能要求。

## 2. 证据与现状

### 已核对事实

- 视频时长约 232.5 秒，展示了 Codex、WorkBuddy、豆包、Cursor 等成员卡片，以及“一个项目、不是一个文件夹”“文件是它们之间唯一的信使”“AGENTS.md 项目协议”等概念。
- 工作台当前服务健康，台账版本为 `0.8.0`，已有虚拟部门四阶段：主管、主执行人、独立复核、整合秘书。
- Codex 已能通过本机已登录 CLI 执行主管拆解和独立复核；调用结果自动写回部门阶段。
- 当前 Agent 名称大多是台账成员，WorkBuddy、Cursor、豆包尚未形成统一的真实双向任务适配器。
- `departmentRun.discussion` 保存阶段讨论留痕，但还没有项目级消息流、回复关系、消息投递状态和实时更新。
- 材料库已有检索入口；用户要求保密原件由人工脱敏，Ollama只做基础汇总和进度整理。

### 未实现事实

- Codex还不是持续运行的监督循环；目前主要由页面按钮启动。
- Cursor完成任务后不能自动把文件、测试和结果回传工作台。
- WorkBuddy建议不能自动进入项目讨论并转化为候选任务。
- 文件主要是路径登记，不是带版本、哈希、提交者和复核状态的成果对象。

## 3. 参考项目调查

| 项目 | 可复用设计 | 不直接照搬的部分 |
|---|---|---|
| [KiroCrew](https://github.com/kirodotdev/KiroCrew) | 持久工作区、任务运行器、会话恢复、消息和审批、项目规则文件 | 它的 ACP 运行时与本工作台现有 Node/JSON 架构不同 |
| [HALF](https://github.com/keting/half) | 人在回路、DAG任务、Git协作仓库、轮询结果 | 其“生成提示词再人工粘贴”不能满足本项目减少人工搬运的目标 |
| [October Bus](https://github.com/october-dev/october-bus) | Agent身份、消息、任务所有权、生命周期、人类升级 | 需要裁剪为本机单用户部门，不引入不必要的网络服务 |

共同结论：消息、任务、成果、Agent会话、审批必须是可追踪的一等数据对象；不能只依赖一个大提示词或一个聊天窗口。

## 4. 目标架构

```text
用户目标
   ↓
项目房间（project room）
   ├── 项目协议：AGENTS.md、约束、敏感级别
   ├── 任务图：父任务、子任务、依赖、责任人、截止时间
   ├── 项目消息：讨论、回执、建议、阻塞、决定
   ├── 成果对象：文件、版本、哈希、测试、复核状态
   ├── Agent会话：Codex / Cursor / WorkBuddy / Ollama
   └── 审批记录：用户确认、Codex决定、返工理由
              ↓
       Codex监督循环
              ↓
    Adapter连接真实Agent
```

### 4.1 核心对象

```json
{
  "projectMessages": [{
    "id": "msg-001",
    "runId": "run-001",
    "sender": "codex",
    "recipient": "all",
    "type": "task_assignment",
    "text": "请 Cursor 完成接口改造并提交测试结果。",
    "relatedTaskId": "task-001",
    "replyTo": null,
    "status": "posted",
    "createdAt": "2026-10-09T00:00:00.000Z"
  }],
  "artifacts": [{
    "id": "artifact-001",
    "runId": "run-001",
    "taskId": "task-001",
    "name": "接口改造说明.md",
    "path": "D:\\项目\\接口改造说明.md",
    "createdBy": "cursor",
    "version": 1,
    "sha256": "...",
    "status": "submitted",
    "reviewStatus": "pending"
  }]
}
```

### 4.2 消息类型

`goal` 目标、`task_assignment` 派工、`ack` 收悉、`progress` 进展、`suggestion` 建议、`question` 提问、`blocker` 阻塞、`artifact` 成果、`review` 复核、`decision` 决定、`system` 系统事件。

每条消息必须关联 `runId`；任务相关消息还必须关联 `taskId`。只有 `decision`、`approval` 和 `artifact` 能改变项目状态，普通聊天不能直接推进阶段。

## 5. Agent职责与权限

| Agent | 主职责 | 允许动作 | 禁止动作 |
|---|---|---|---|
| Codex | 总管、拆解、监督、复核、项目决定 | 建任务、派工、追问、退回、发布决定 | 绕过审批执行不可逆外部动作 |
| Cursor | 代码和文件执行 | 读取授权工作区、修改文件、运行测试、提交成果 | 自己批准自己的成果 |
| WorkBuddy | 建议、风险和替代方案 | 读取脱敏项目上下文、提交建议 | 擅自改目标或覆盖最终成果 |
| Ollama | 基础汇总、进度对齐 | 处理低敏文本和结构化状态 | 读取保密原件、做最终裁决 |
| 用户 | 目标、脱敏、关键取舍 | 提交目标、批准高风险动作、否决决定 | 不再承担日常搬运和催办 |

系统应在 Adapter 层检查 `sensitivity`：保密材料没有脱敏证明时，不得进入 Ollama、WorkBuddy 或外部 Agent 请求。

## 6. 监督循环

```text
1. Codex读取项目协议、任务图和最近消息
2. 判断是否存在可执行任务
3. 创建/更新子任务并派给Cursor或WorkBuddy
4. 等待ack、progress、artifact或blocker
5. 检查超时、文件存在性、测试结果和敏感级别
6. 将WorkBuddy建议转为候选任务或风险记录
7. 对Cursor成果执行复核
8. 通过：解锁下游；退回：保留原成果并创建返工
9. 冲突或不可逆动作：请求用户决定
10. 写入项目决定和下一次唤醒时间
```

监督循环必须幂等：服务重启不能重复派工；同一 `taskId` 和 `attempt` 只能有一个活动执行；失败要保留错误和重试次数。

## 7. MVP范围

### M1：项目群聊与成果对象

- 为部门工作链增加项目消息流；
- 增加消息筛选、回复、未读和阶段关联；
- 增加成果对象、版本、哈希、提交者和复核状态；
- 现有人工回填统一改为消息和成果提交。

验收：用户创建项目后能看到 Codex、Cursor、WorkBuddy 的结构化消息；成果文件能在项目内打开并显示版本与复核状态。

### M2：Codex自动派工与监督

- Codex拆解后自动生成子任务；
- 自动写入 Agent 收件箱；
- 提供 ack、doing、blocked、done 回执；
- 超时、空结果和失败自动提醒 Codex；
- 复核退回自动创建返工任务。

验收：用户只提交一次目标，不手工复制任务；模拟 Cursor 延迟和失败时，项目状态正确进入阻塞或重试。

### M3：Cursor执行适配器

- 统一 `health / submitTask / readResult / cancel` 接口；
- 自动收集修改文件、测试命令、测试输出和错误；
- 成果提交前进行敏感级别和路径检查。

验收：一个真实代码任务从 Codex派工到 Cursor回传，文件和测试结果完整进入项目房间。

### M4：WorkBuddy建议适配器

- Codex可以针对一个任务发起建议请求；
- WorkBuddy回复进入项目消息流；
- Codex可将建议转成任务、采纳或驳回，并记录理由。

验收：WorkBuddy只提供建议不会越权修改最终结果；建议被采纳后能追溯到对应任务。

## 8. 不纳入MVP

- 不把所有Agent放进同一个无限上下文；
- 不让Ollama读取保密原件；
- 不默认自动发送外部消息、删除文件或发布成果；
- 不引入多机集群、复杂分布式数据库或公网协作；
- 不把Agent名称登记误认为真实连接。

## 9. 技术选择

- 保留现有 Node.js HTTP 服务和 `data/store.json`，M1不迁移数据库；
- 用事件对象模拟消息总线，所有状态变化同时写入台账和项目消息；
- 用 SSE 或短轮询实现项目房间刷新，先不引入WebSocket；
- Adapter 使用本机进程、HTTP或文件投递三种实现，统一返回同一格式；
- 高风险动作沿用显式用户确认；
- 继续保留人工脱敏边界，并在服务端再次检查材料级别。

## 10. 开发顺序与确认门

1. 先更新正式 SPEC，确定消息、成果、Adapter和监督状态机字段。
2. 增加 M1 数据模型、接口和项目房间界面。
3. 编写消息、成果版本、重复投递、权限和重启恢复测试。
4. 通过 M1 验收后，再开发 Codex自动监督。
5. 再分别接入 Cursor和WorkBuddy，避免把两个未验证连接同时引入。

本方案是开发前基线。根据工作区规则，只有用户明确发送 `Confirm Development` 后，才开始正式编码。

## 11. 当前待确认的三个决策

1. **Cursor接入方式**：优先本机CLI/IDE桥接，还是先用文件投递适配器验证闭环？这决定 M3 的实现路径。
2. **项目房间刷新方式**：先采用短轮询，还是直接引入 SSE？这决定服务端连接管理复杂度。
3. **Codex裁决边界**：Codex是否可以自动通过低风险文件成果，还是所有成果都必须由你最终点击确认？这决定监督循环的自动化程度。

## 12. M2项目聊天工作界面（本次需求修正）

M1的项目讨论区只是消息展示，不能称为聊天工作界面。M2必须以“项目房间”为主要工作面，用户在一个窗口内看到成员、讨论、派工、回执和成果。

### 12.1 新建项目

新建项目表单必须一次完成：

- 项目名称；
- 总目标；
- 背景与约束；
- 可共享材料；
- 勾选参与成员；
- 每个成员的角色或能力；
- 是否允许自动推进；
- 关键成果和截止时间。

创建后生成 `projectRoom`，参与成员固定在该项目范围内，不再从全局 Agent 名单临时猜选。

### 12.2 项目房间布局

```text
┌──────────────┬───────────────────────────┬──────────────┐
│ 项目成员      │ 项目群聊                  │ 任务/成果     │
│ Codex 总管    │ Codex：目标已拆成3项      │ 任务树        │
│ Cursor 执行   │ Cursor：已接收任务1       │ 当前负责人    │
│ WorkBuddy建议 │ WorkBuddy：建议先检查…   │ 文件版本      │
│ Ollama秘书    │ Codex：采纳建议并派工     │ 风险/决定     │
│ 用户          │ 用户：补充一个约束         │ 待确认动作    │
└──────────────┴───────────────────────────┴──────────────┘
```

中间区域必须有输入框。用户可以追加约束、追问或改变目标；消息进入项目台账后，由 Codex决定是直接回应、更新任务，还是重新派工。

### 12.3 首次启动流程

```text
用户新建项目并勾选成员
→ 系统建立项目房间
→ Codex自动发言：确认目标、列出任务、说明依赖
→ Codex向Cursor派发执行任务
→ Codex向WorkBuddy发起建议请求
→ 成员回执进入同一消息流
→ Codex比较建议与执行结果
→ 通过、返工或请求用户决定
```

### 12.4 真实接入边界

项目房间的消息不能伪装成真实 Agent 回复。每条 Agent 消息必须带有：

- `source`: `codex-cli`、`cursor-file-drop`、`workbuddy-file-drop` 或 `manual`；
- `jobId` 或 `submissionId`；
- `createdAt`；
- `relatedTaskId`；
- `deliveryStatus`。

在 Cursor 和 WorkBuddy 适配器完成前，界面应明确显示“人工/文件回执”，不能显示成“Cursor正在工作”。

### 12.5 本次M2验收标准

1. 新建项目时可以勾选参与成员，创建后成员列表固定。
2. 项目房间有真实输入框，用户发送内容后立即进入消息流和台账。
3. Codex拆解结果以多条结构化消息出现，并自动关联任务。
4. Cursor任务、WorkBuddy建议和Codex决定出现在同一时间线。
5. 每条消息可追溯来源、任务和投递状态。
6. 用户刷新页面后，项目房间、消息和任务仍完整恢复。
7. 没有真实接入的 Agent必须明确标记为人工/文件回执。

M2不是在M1讨论区上再加一个输入框，而是把项目房间设为项目工作的主入口；四阶段工作链、任务树和成果面板都从房间中展开。
