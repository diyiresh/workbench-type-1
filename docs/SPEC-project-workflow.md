## 2. 新旧流程与角色

### 2.1 版本及身份

新增 `workflowVersion: 2` 表示本次三角色节点流程。无此字段或值为 1 的项目继续走历史实现。不得用 `collabVersion` 推断新流程或改变旧项目。

M1 先允许显式创建新流程的隔离试点；完成新入口与兼容验收后，新建界面采用新流程。旧接口行为保持兼容；只读投影不得生成方案、派单或迁移记录。

业务项目（`modules`）、协作工作链（`departmentRuns`）、实际调用（`executionAttempts`）与文件记录使用原有独立 ID。业务关联仅通过明确 ID 引用，不依名称合并。

### 2.2 角色契约

新流程三角色内部键复用 `director`、`executor`、`reviewer`，界面分别显示项目负责人、具体执行人、独立审核人。仅复用身份术语，不复用旧的固定四项执行顺序。

`run.roleAppointments` 保存当前三角色及任命修订；每个工作单元冻结 `appointmentRevision` 和实际 `ownerAgentId`。三人必须不同。工作单元的用途采用独立 `purpose`，不能仅按角色推断执行步骤。

新流程不创建 secretary 固定岗位。执行人完成送审前必要整合，审核通过后负责人整理交付说明、清单及附后事项，不再次自动改写正文。旧秘书记录和文件照常可查。

角色变更必须记录真实授权主体和原因。已有占用、待核对或领取记录时，先按原执行治理处理旧归属；不能改一个成员 ID 就视为安全换人。

## 3. 方案、意见与批准

### 3.1 持久化结构

在现有 run 中增加如下数据，不另建进度文件：

| 数据 | 最小约束 |
|---|---|
| `workflowRevision` | 每次有效业务命令递增；并发写采用预期修订 |
| `roleAppointments` | 三角色、修订、任命来源和时间；历史任命不可覆盖 |
| `planVersions` | 不可变的方案版本、规范化内容哈希、提交人真实尝试引用 |
| `planFeedback` | 意见 ID、来源角色/成员、所评方案版本及哈希、实际尝试引用 |
| `planResolutions` | 负责人对每条意见的采纳、部分采纳或不采纳及理由 |
| `planApproval` | 方案版本/哈希、任命修订、交付约定哈希、必要授权与批准记录 |
| `milestones` | 稳定 ID、依赖、截止时间、成果标准、工作单元及审核引用 |
| `supervision` | 批准的有限检查安排、去重事件、累计检查额度和下一检查点 |

方案内容至少包含目标、范围、路径、节点依赖、预期成果、验收标准、执行和审核分工、交付时间、检查时点和联系对象、主要依赖与应对安排。哈希覆盖内容及顺序，采用稳定规范化序列化；不得散用对象属性插入顺序作为版本判断。

意见绑定不可变版本。新增意见不修改方案内容，不使同时返回的另一位成员意见被旧对象覆盖。负责人修改内容应产生新版本，并显式记录意见来源和处理结果。

### 3.2 最小完整顺序

1. 董事长指定三角色，可先保存缺项草稿；创建本身不调用成员。
2. 通过角色能力检查后，为负责人创建拟案工作单元。
3. 执行人、审核人对同一方案初稿各提交一轮意见；补充征询仅限明确差异并计入原预算。
4. 负责人处理意见、定稿；缺失意见必须可见，不编造同意，不自动越过征询。
5. 董事长批准确切定稿快照及必要任务授权。
6. 按批准节点执行、生成文件、独立审核、负责人交付、董事长验收。

方案批准不等于泛化的 Start Writing 或 Confirm Development。界面可在同一动作明确收取所需授权；批准记录必须可证明用户同意了什么。已批准范围不得重复索要同一许可。

### 3.3 状态权威

`run.status` 仍是唯一项目业务状态。新流程状态使用 `planning`、`awaiting_plan_approval`、`active`、`review`、`awaiting_files`、`awaiting_acceptance`、`blocked`、`completed`；规划子阶段区分拟案、征询、定稿。

暂停、归档、控制代数沿用旧字段；不把暂停包装成新业务完成状态。`executionAttempts.state` 仍只描述一次调用；心跳、成员自报、实际成果、审核通过和董事长验收分别展示。

## 4. 命令、来源与并发

所有写命令均限既有本机受控入口，携带 `idempotencyKey`、`expectedWorkflowRevision`、`expectedGeneration`。方案相关命令还携带所绑定 `planVersionId`、`planHash`；批准额外绑定 `appointmentRevision` 和交付快照。只读 GET 不需要批准，也不能触发工作。

幂等范围至少包含 run ID 与命令用途；同键同内容返回原回执，同键不同内容拒绝。先查历史回执，再校验新的预期修订，避免成功后的重复提交被错误拒绝。

成员来源不得相信请求中的 `agentId`。后台必须从真实尝试、claim、对应工作单元、控制代数和冻结任命解析实际主体，再校验用途和权限。只读 CLI 返回结构化建议时，后台从该次受控调用绑定主体；正文自称身份不能提供授权。

读取和提交均检查暂停、归档、当前方案与任命。迟到结果保留为 held，不推进。不可用新流程版本、计划检查用途、新时间戳或新工作单元绕过旧调用/复核预算。

| 接口（待实现） | 权限与主要约束 |
|---|---|
| `GET /api/departments/runs/:id/workflow` | 新旧流程只读投影，旧项目原始记录不变 |
| `POST .../plan/draft` | 负责人实际拟案尝试；提交不可变初稿 |
| `POST .../plan/feedback` | 执行人或审核人实际意见尝试；准确版本，不能自造他人意见 |
| `POST .../plan/finalize` | 负责人实际定稿尝试；记录意见处理和差异 |

| `POST .../supervision/check` | 仅既有内部巡检产生到期事件；未批准、暂停或占用时不重发 |
| `POST .../supervision/action` | 实际负责人检查尝试；受控调整、追进度、返工与安全改派 |

## 7. 负责人推进、文件与兼容不变量

- 复用现有每分钟 duty tick，只产生持久化去重事件。有限检查安排和每节点累计预算来自批准方案，不新增通用模型轮询角色或常驻循环模型。
- 同成员最多一个有效调用；忙碌时等待，不为了查询进度并发启动第二次调用。
- 普通技术问题进入负责人待办；需要董事长手动启动成员时才生成技术协助卡。方案审批、验收和实质范围变更仍按原业务权限。
- 恢复/改派保留原始输出、重试和复核预算。旧会话未停止或归属不明，不重新派发。
- 文件沿用 delivery 实际路径、大小、哈希、源版本与审核快照；正文通过不替代文件通过。交付后文件改动使相关核验失效。
- 不自动迁移旧项目；显式迁移先只读预览，处理有效调用后保持暂停，保留历史与预算。
- C3 操作能力全保留，界面合并须列旧入口对应；思考独立、双项目入口、可选全员回复/v2 组织能力保留；细分知识/报告导航后移。

## 10. 当前状态转换与故障归口（第二轮复核补充）

本表描述实际实现。工作单元的 queued/doing/done/blocked 与项目业务状态分开；调用 returned 也不代表项目验收。

| 当前项目状态/子阶段 | 谁可推进 | 必要证据 | 下一状态 |
|---|---|---|---|
| planning / capability | 既定三名成员通过运行通道 | 真实角色验证尝试、准确读回、配置指纹及有效期 | planning / draft |
| planning / draft | 实际负责人 | 当前负责人绑定尝试、完整结构化方案 | planning / feedback |
| planning / feedback | 执行人及独立审核人 | 同一方案哈希的两份实际意见 | planning / finalize |
| planning / finalize | 实际负责人 | 完整定稿、对每份意见的处理理由 | awaiting_plan_approval |
| awaiting_plan_approval | 董事长界面 | 专用批准口令、准确方案/任命/交付快照及相应写作/开发许可 | active |
| awaiting_plan_approval | 董事长要求修订，负责人定稿 | 原方案版本、具体意见、新的不可变定稿 | planning / finalize，随后重新批准 |
| active | 当前节点执行人 | 绑定实际尝试及完整结果，未暂停且输入未变化 | awaiting_files 或 review |
| awaiting_files | 现有文件生成器 | 冻结执行稿、实际文件及文件/读回快照 | review |
| review | 既定独立审核人 | 批准标准逐项证据；文件项目逐份实际读回摘录；冻结执行结果哈希 | 下个 active 节点，或负责人交付后 awaiting_acceptance |
| review | 既定独立审核人退回 | 明确不符合项和真实审核尝试，保留原稿及原预算 | blocked，由负责人组织处理 |
| blocked | 实际负责人 | 绑定尝试的证据或明确缺口；重试/改派/核对均须各自门禁 | 保持 blocked 或恢复当前节点 |
| awaiting_acceptance | 董事长界面 | 专用批准口令、实际文件未变、最终交付快照一致 | completed |
| 任意未归档阶段 | 董事长控制，后台保存迟到结果 | 准确控制代数和暂停/恢复记录；暂停后旧调用结果只保留 held | 原业务状态保持，改变暂停控制字段 |
| 归档/旧流程 | 原流程及既有治理 | 不自动转换、不恢复、不重发 | 保持原状态 |

| 现象 | 默认归口 | 默认动作 | 是否需董事长介入 |
|---|---|---|---|
| 普通逾期、等候领取、执行或审核退回 | 项目负责人 | 查看实际回执/缺口，原预算内处理；不自动追加次数 | 否 |
| 执行人/审核人确因登录或依赖不能工作 | 项目负责人先核实 | 仅明确 auth_required/dependency_unavailable 时提出人工启动协助 | 仅必要的手动启动 |
| 负责人通道自身不能运行 | 执行治理保留现场 | 显示具体启动请求，不偷换负责人 | 必要时手动启动该成员 |
| 重启、超时、旧结果未核对 | 项目负责人 | 保留原调用/成果，先核对关闭证据，不盲目重发 | 通常否 |
| 预算耗尽 | 项目负责人 | 交付已有成果、缺口和状态，不静默清零 | 仅涉及实质范围/资源决定时 |
| 实际文件变动/缺失 | 项目负责人及文件交付器 | 原稿生成新批次、保留旧批次、重新独立审核 | 最终验收仍由董事长 |
| 台账短暂占用 | 台账写入模块 | 最多约 400ms 退避等待；忙超时返回 409 | 否 |
| 台账持锁进程已退出 | 台账写入模块 | 核实 PID 确已不存在后回收，记录日志；不以时间过长代替退出证明 | 否 |
| 台账同一节发生冲突 | 原调用方/实施人员 | 拒绝旧快照；重新读取核实，不直接覆盖或自动重放外部调用 | 否 |
| 批准口令未设置 | 董事长本人 | 本机终端手动 setup，口令不发聊天 | 是，独立身份初始化 |

### 10.1 检查报告与事件终态

负责人报告必须提交 evidenceRefs 和 unknowns。每项引用须来自本项目已有 executionAttempt、不可引用本次检查自身、不得重复，且 resultHash 与台账一致；后台保存当时状态快照。没有可确认回执时允许明确列出 unknowns，不伪造进度。

检查尝试成功应用后，对应检查事件 completed 并关联 attemptId；失败则 failed。节点已有独立审核通过的成果时，未执行的旧检查标 superseded，不冒充已经检查。以上只关闭检查请求，不关闭仍受阻的节点、执行回执或实际交付问题。重复应用同一尝试不重复生成报告。

### 10.2 非实质修订边界

采纳“避免为排期文字重复审批”的方向，但本轮不开放无条件改截止时间的旁路。当前实现仍以不可变方案和原批准快照为准；未实现独立的排期调整命令。

后续可将批准的最晚期限内调整内部检查时点、联系对象、且不减少验收内容/检查预算/独立审核的修改，记录修改人、原因、前后值及原批准引用，作为非实质修订。改变承诺交付期限、依赖、资源、验收内容或增加调用预算，不自动归为非实质修订。该细化须在实现时给出明确受控命令和反例验证，不能只改文档就声称已有此能力。

### 10.3 写锁适用范围

所有通过 createLedger 写入的本机进程使用同一互斥协议；先按唯一候选票据排序，再原子发布包含 PID 的最终锁文件。确证进程退出才清理其唯一候选及残留锁，防止两个回收者删除新持锁者的文件。进程仍活着或无法确认时限时等待，超时明确报错。PID 被复用时保守不抢锁。

仅适用于同一台机器、本地支持原子重命名/硬链接的文件系统；不声称支持跨机器云同步竞争。绕过模块直接编辑 store.json 的程序不受锁约束，应通过本机 API。异常 JSON 锁不凭空推断持有人，需要实施人员核实。
