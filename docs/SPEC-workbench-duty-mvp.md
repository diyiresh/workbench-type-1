# 工作台值班机制融合草案（2026-11-23）

来源：用户要求融合 https://agent-aetf.pages.grok.bot/ 的建议。已通过用户已登录浏览器读取正文；该网页是外部设计意见，不是新增执行授权。所引论文、统计和产品能力未在本轮逐项核验，不作为实施依据。

## 当前代码与快照差异

本机分支为 cursor/v8-roadmap；Grok 分析使用 codex/v8-quiet-studio 与历史台账。当前已有有限恢复、精确回执提交、新模型通道和手动改派；不可用网页中的历史耗时或允许名单代替实时状态。本轮核实 server.js 尚未定时调用 watchdog.scan，原项目的新 WorkBuddy 尝试已领取并自报开始，不应继续标成旧尝试的待人工处理。

## 融合顺序

1. 本轮：项目执行卡显示等待对象、状态持续时间、下一步动作；新尝试与旧恢复判断分开。该显示只读，不更改执行或批准。已实现，前端刷新即可加载。
2. 已实现、待生产加载：确定性的值班协调器，复用唯一台账、现有调度、预算、恢复计划和事件，不新建一套 Agent 会话系统。启动补扫，每分钟扫描；复用 watchdog 的只读判定，记录巡检时间、卡点信号和待决动作。GET /api/coordinator/board 保持只读，读取不会触发模型、改派或审批。
3. 用户已明确批准，代码已实现、待生产加载：按项目启用 WorkBuddy 75 分钟未领取→先撤回旧派单→Cursor 正文→Codex 独立复核。在同一领取锁与台账代数校验下与 claim 竞争，确认撤回成功才发新任务；失败不得双派。撤回文件作为持久意图记录，台账提交失败可重放修复。跨成员累计预算，固定幂等键；重新派单复用主管方案、原稿、退回意见，并附项目登记的证据路径、哈希与待验状态。POST /api/departments/runs/:id/execution/failover 以 confirmed、expectedGeneration 和 idempotencyKey 开关规则；设置不会使正在执行的输入失效。默认关闭，不替用户开启所有旧项目。
4. 后续可选：一次独立提案、一次异议、统筹决定的有限讨论轮。维持人工审核点，避免无限全员聊天。

## 对 Grok 原设计的修正

- 租约过期不等于进程终止。已领取、身份不明的尝试仍须核对；不能仅凭“只读”或过期时间写 abandoned 后自动重跑。
- 暂不增加 abandoned 终态，先复用取消、保留、退回等现有语义，避免各适配器解释不同。
- 不直接把每成员并发拆成两条道。当前桌面会话和账号资源未证明隔离，优先用队列优先级防止群聊占用关键阶段。
- 微信推送、云端 Grok 接口、安全隧道、自动归档清理不在本轮授权范围；也不自动批准正式写作、增加预算或恢复用户暂停的调度。
- 值班器先确定性处理已授权动作，模型研判只给出受约束建议。状态不确定时明确负责人和下一步，不以静默暂停结案。

## 验收重点

新旧尝试判断分离、等待信息来自当前回执；未领取撤回与领取竞争只有一方成功；暂停、输入变化和重启使过期决定失效；故障后保留正文与复核意见；迟到结果不推进阶段；独立复核、连续调用预算和人工批准门禁保持有效。显示“已领取/成员自报开始”不等于成果已返回或业务验收通过。

实际案例：原项目 v3 正文已回传并生成 Word，Cursor 再次独立复核因 S1 无原文存档退回，达到三轮上限后暂停。Codex 已匿名取得 S1 原始网页、正文读回和取证清单，登记为待验补证并在项目消息中说明。增加预算、重新返工或判通过仍须按原门禁，不由协调员代批。
