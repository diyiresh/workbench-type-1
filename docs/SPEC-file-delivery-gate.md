## 目标和 MVP

- 保持四岗位、唯一台账、已有写作授权、独立复核、暂停/归档和有界重试规则。
- 增加显式交付要求：正文即可，或需文件；文件项目明确格式、数量、源版本和输出目录。主管发现目标与交付要求冲突时标为待确认，不能默认为文字交付。
- 文件项目区分内容就绪、文件待生成、文件待复核、文件交付通过。缺文件、不可读或版本不匹配不得进入交付完成。
- 首期提供已批准 Markdown 正文转 DOCX，以及已有本机文件的核验登记。不会重新研究或改写已批准正文。
- 项目内提供成果清单：文件名、版本、实际路径、大小、SHA-256、源正文哈希、独立复核状态，以及打开文件/所在目录入口。
- 现有文本项目仍可完成；历史项目保留阶段结论，显示“文件交付未核验”。不批量重跑历史工作链。
- 若确认包含当前报告补交，使用真实董事长消息所指定、已通过内容复核的版本，将长篇、摘要、附件分别导出。桌面位置从 Windows 已知文件夹读取，禁止猜测路径。

## 技术与复用选择

沿用 Node.js 服务、现有页面和 `data/store.json`，增加独立交付模块，不建立第二份进度台账。

| 开源项目 | 可复用部分 | 取舍与风险 |
| --- | --- | --- |
| [dolanmiu/docx](https://github.com/dolanmiu/docx) | Node.js 生成段落、表格、页眉页脚等 DOCX；MIT | 推荐首期采用。需要显式处理 Markdown 和中文排版，必须验证表格及文本完整性。 |
| [jgm/pandoc](https://github.com/jgm/pandoc)、[用户手册](https://pandoc.org/MANUAL.html) | Markdown 转 DOCX、reference-doc 样式 | 备选适配器。引入外部可执行程序及部署依赖；转换成功不代表内容、版式或交付验收通过。 |

DOCX 导出应由本机工作台的确定性转换器执行，成员提交正文与源版本。桥接 JSON 继续承担任务回执，不冒充最终业务文件。文件格式之外的代码、安装包、PDF 等交付器留待后续，不在本期承诺支持。

## 接力顺序与完成条件

主管明确交付要求 → 执行人提交正文 → 工作台生成文件 → 独立复核人检查正文和实际文件 → 整合人提交交付清单 → 工作台重查文件与版本 → 交付通过。

整合人如改写了正文，必须生成新版本并重新复核；旧版本的通过结论不能自动沿用。既有项目已完成内容复核时，可补交文件并单独进行文件复核，保留原内容复核历史。

登记时实际读取文件，服务器计算大小及 SHA-256；复核记录绑定源版本和文件哈希。完成、下载或打开前重查，文件被修改、删除或替换后显示核验失效，不继续宣称当前文件已验收。

目录权限或转换失败明确显示阻塞，保留已生成文件与正文；重试不能重复调用正文写作或覆盖旧成果。后台落盘失败不得先提交完成状态。异步结果遇到归档或暂停时只留待处理记录，不能继续派发。
