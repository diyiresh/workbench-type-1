# 工作台精简优化开发计划

版本：计划稿 v1。编制日期：2026-11-24，Asia/Shanghai。

依据：董事长已确认的《流程图修订稿 v3》、四页纸面批注及后续澄清。流程确认完成，开发计划待审；本轮只编制计划，不修改工作台程序、不启动业务成员、不部署或推送。

## 1. 项目目标与交付边界

把工作台改造成由项目负责人主导、能先形成可靠方案、主动掌握节奏并交付成果的本机协作系统。董事长在工作台下达目标、指定三角色、批准最终方案、查看阶段成果并验收，只对项目负责人；普通推进问题由负责人组织解决。只有 Agent 无法工作且确需董事长手动启动时，负责人提出人工操作协助请求。

本期重点是项目模块及其直接依赖的执行、调度、回执和交付机制。沿用现有四个工作入口“今日、项目、思考、知识库”；思考独立保留；业务项目与协作任务继续分为两个入口。既有操作功能全部保留，重复界面入口可以合并。取消固定整合岗位，但执行过程中的必要整合和送审前定版继续保留。全员分别回复、v2 组织能力保留，不变成每个项目的必经步骤；知识与报告的过细分类优化后移。

完整交付包括：新项目流程、计划协商与审批、负责人主动推进、统一项目视图、真实成果和文件验收、Grok Bot 适配、历史兼容、自动与真实通道验收、上线与回滚说明。Grok 的真实接入是独立验收项，不能以“成员列表里有名字”代替完成。

### 1.1 验收的实际结果

- 新建项目时由董事长明确指定负责人、具体执行人、独立审核人；系统不擅自沿用旧的默认三成员分工。
- 负责人拟初步方案，征求执行人与审核人意见，处理分歧后形成最终方案，董事长同意后才能执行。
- 每个批准节点都能在工作台看到对应成果或真实未达成状态、负责人处置和下一检查点；无需进入其他 Agent 界面追问。
- 负责人主动了解进度、协调依赖、组织返工和必要的换人，普通技术阻塞不再作为“请董事长决定怎么修”的事项上交。
- 文件项目只有在实际文件、源版本和独立审核相符后才能交付。董事长验收、正式报送与归档分别记录。
- 不丢原稿、历史意见、暂停设置、调用预算或用户未保存草稿；刷新页面不触发模型、重派或审批。

本机代码基线为 main `12b15709dd0f2322a13cec1fbc68eb35e5d23a10`。此前第一批已移除经典布局和 24 个主题并统一主线，本期不重复开发这些内容。

本轮只读台账快照为 4 个业务项目、3 条协作工作链，其中 2 条已归档完成、1 条返工；检查时未发现正在执行的调用。该快照只用于设计迁移与试点，不能据此改写、恢复或重新派发任何历史项目。上线前重新读取当时的实际状态。

此前 84 项后端和 31 项界面回归通过是上阶段记录，不是本期新功能的验收结果。

## 3. 技术选择与系统架构

### 3.1 沿用现有栈

继续使用 Node.js 本机 HTTP 服务、原生 ES Modules/CSS、既有路由模块和 `data/store.json` 唯一业务台账；文件交付继续使用已有 docx 转换与核验。沿用当前 Playwright 和隔离数据目录测试。保持仅本机访问的默认边界和四主题、中英文、窄屏支持。

本期不引入 React、PostgreSQL、Redis、工作流平台或第二套 Agent 守护服务。先把现有事实和调度责任归一，再评估性能。若实际压测表明现有台账不能承受需求，单独提出有证据的后续方案，不在本期顺手换库。

### 3.2 五个层次及唯一责任

| 层次 | 责任 | 权威来源 |
|---|---|---|
| 项目界面 | 目标、任命、方案审批、进展、成果、讨论与集中操作 | 读取下层投影；不在浏览器独立计算业务完成 |
| 项目流程 | 方案版本、意见处理、节点依赖、负责人动作与最终验收 | 同一项目记录及版本化命令 |
| 主动推进 | 检查到期节点、收集进度、发现阻塞、安排负责人处理 | 持久化检查点与事件；复用现有 duty-coordinator |
| 执行治理与通道 | 实际派发、并发、领取、输入快照、结果、会话停止、迟到保留 | executionAttempts；jobs 只引用尝试 |
| 成果与存储 | 实际文件、版本、审核绑定、原子落盘及恢复 | 现有 delivery、ledger-store 与实际文件证据 |

负责人模型负责判断与建议，后端负责校验和执行。只读成员可以返回结构化行动建议，由后端绑定其真实尝试和任命归属后执行受控命令；不因此开放业务文件写权限或假定 CLI 能直接调用所有本机接口。模型说“已派发”“已完成”不直接改变阶段；只有经过受控命令及实际回执才入账。新增负责人逻辑不得另起第二套项目队列、状态表或定时器。

## 4. 角色、权限与沟通关系

| 角色 | 必须承担的职责 | 可做的业务操作 |
|---|---|---|
| 董事长 | 定目标、指定三角色、同意最终方案、验收；必要时手动启动 Agent | 批准明确版本的方案、暂停/恢复、确认验收；不承担普通故障排查 |
| 项目负责人 | 拟方案、征求意见、处理分歧、定稿；安排检查节奏、主动找人、协调解题、交付 | 在批准方案和原有授权范围内创建工作单元、催取进度、调整方法、组织返工及必要改派 |
| 具体执行人 | 对方案提可行性意见，执行任务，向负责人如实反馈进度和成果 | 领取自己的工作单元、提交与本次输入绑定的实际结果 |
| 独立审核人 | 对初步方案提意见，独立检查正文及实际文件，给出具体通过或退回依据 | 提交方案意见和绑定实际版本的审核；不能替执行人自审 |

本期按三名不同成员校验新项目任命。被指定成员必须具备对应角色的已验证通道能力；仅登录、进程存在或短文本连通不代表胜任负责人或实际文件审核。不满足时项目可保存草稿，但不能伪装已启动，也不能暗中换成其他成员。

负责人是董事长的唯一业务对接人。原始执行和审核记录可以展开查看，但默认项目反馈由负责人组织。成员故障、材料不全、普通返工由负责人处理；需要董事长亲自操作的 Agent 启动请求，须具体说明启动对象、当前卡点及启动后由谁接续，完成启动后仍由负责人推进。

方案批准和最终验收属于原定业务决策，不等同于把技术问题升级给董事长。目标、范围或验收标准发生实质变化时，仍按既有规则修订方案并取得必要确认；不能用“负责人负责”扩大原授权。调用预算用尽时不得静默清零或伪造新输入绕过限制，负责人在约定节点交付已有成果、真实缺口和处置状态，不把排障选项反复转交董事长。

## 5. 新项目业务流程与方案审批

### 5.1 新建与初步方案

新建表单填写目标、预期成果与格式、约束和材料，分别指定三角色；可明确关联已有业务项目。三角色任命与可用能力检查在启动前完成。创建本身不批准写作、不自动开始正式执行。

负责人收到的是“形成可推进方案”的任务，而非转发邀请。初步方案采用结构化内容：目标和范围、主要推进路径、节点及依赖、各节点成果与验收标准、执行和审核分工、交付时间、主动检查时点与联系对象、主要依赖与应对安排。系统允许负责人补充实质缺项，但不能自动给董事长增加一份冗长问卷。

### 5.2 意见、定稿与批准

执行人与独立审核人分别收到同一初步方案版本，可提交修改意见或明确无异议。默认完成一轮有针对性的征询；必要补充只围绕未解决的差异并遵守现有预算，不增加无限多轮讨论机制。

每条意见记录来源、方案版本、问题和建议。负责人决定采纳、部分采纳或不采纳并给出简短理由，组织成最终方案；缺少反馈要如实标明，不能编造“双方已同意”。反馈未返回时由负责人追进度、判断安排，不把成员原始讨论直接转给董事长。

董事长看到最终方案、阶段节点与关键待确认事项，一次批准确切的方案版本和三角色任命。正式写作仍满足 Start Writing；完整开发仍满足 Confirm Development。界面可以在同一确认动作中明确取得本任务所需的授权，不以一次空泛“同意”替代明确许可，也不在已批准范围内重复索要确认。

批准记录绑定方案哈希、版本、任命修订、交付约定及授权范围。过期页面、被改动的方案或重复点击不得批准错误版本。同一批准重复提交只得到同一回执。

### 5.3 执行、审核与交付

批准后按节点创建实际工作单元。执行人完成必要整合，工作台按交付约定生成实际文件，独立审核人核对内容、文件和版本，负责人组织干净交付。取消单独秘书调用，不把“负责人交付”做成另一次自动改写全文；交付只整理清单、结论及必要附后事项。

阶段成果按批准节点主动回工作台，不默认在每个节点要求董事长再次点击才能继续。需要董事长作出业务决定的节点应事先在方案里明确。最终交付由董事长验收；验收、正式报送和 Obsidian 归档分别记录。没有明确归档指令不写入 Obsidian。

## 6. 负责人的主动推进机制

### 6.1 节奏来自批准方案

每个节点至少有预计成果、截止时间、负责人下一检查时间、需要了解进度的成员、依赖和未达成时的处置安排。节点时间由负责人提出并经启动时确认，不统一改为固定每日简报，也不擅自承诺所有成员立即响应。

复用现有每分钟巡检：发现到期检查点、新成果、审核退回、通道不可用或节点逾期时生成去重的负责人待办。确定性判断不调用模型；需要判断或调整安排时才发起一次有界的负责人工作单元。已有成员占用时排队，不能并发向同一成员再发一份追问。

方案列出有限的主动检查点和每节点的模型检查预算；确定性巡检不等于模型调用。调整下一检查时间、生成新 checkId 或改变时间戳，都不能刷新同一节点的累计检查上限，避免把“主动推进”变成另一种无限内部循环。

负责人动作必须落地为可检查结果：已查到的实际进度、依据、新的下一检查点、必要协调或改派命令，以及节点成果引用。只有“继续跟进”“正在努力”不算处理完检查点。进程心跳、成员自报、实际成果返回分开显示。

### 6.2 防止内部空转

到达节点却没有完整成果，也要按约输出已完成部分、真实缺口和负责人正在采取的安排，不能靠持续重试隐藏逾期。相同错误第二次出现须改变方法；调用和复核预算继续有效。回报同一状态采用稳定事件键去重，不产生刷屏式聊天。

负责人在既定授权内可调整方法和协作安排、组织必要的换人；保留独立审核。改派前先撤回未领取派单或确认旧会话停止，记录依据，绑定最新输入和归属，再派下一次。旧派单、输出、审核意见均保留，迟到结果只留痕，不推进新阶段。

原有按项目批准的 WorkBuddy 75 分钟补位规则保留其适用边界，不自动开启所有项目、不擅自启停 WorkBuddy 定时领取。新流程的处置原则纳入方案批准的负责人权限，不能继续伪造 chairman 来源消息。

### 6.3 重启和负责人自身故障

检查点、事件去重键、待执行建议和最后一次真实反馈落入同一台账，服务重启后补查到期事项，不重放未知调用。已领取或可能启动的尝试保持待核对，不能因重启认定未执行。

负责人通道失效时，后端仍保留事实、成果和到期状态；能通过已经批准的恢复安排处理则在预算内处理。确需人工启动该 Agent 时，工作台提供明确的启动协助卡。不能因负责人没有回复就把执行人升格为新负责人，或伪造负责人的业务判断。资源完全不可用时如实保留未达成状态，不承诺无条件自主完成。

## 7. 数据模型、版本与状态设计

仅对新流程增加必要字段。业务项目、协作工作链、执行尝试和实际文件保持不同身份，以 ID 引用连接，不按名称自动合并。

| 数据组 | 拟增加或调整的内容 | 权威与兼容原则 |
|---|---|---|
| 流程标识 | `workflowVersion` 标识新三角色节点流程 | 与现有 `collabVersion` 的 v2 组织能力分开，不新增用户必须理解的版本选择 |
| 角色任命 | 三角色及任命修订、变更原因、执行主体 | 任命是当前角色权威；实际工作单元冻结其所用任命版本，历史不覆盖 |
| 方案版本 | 初稿/定稿、结构化节点、来源、内容哈希、反馈及意见处理 | 已提交版本不可变；修改产生新版本，不覆盖已批准方案 |
| 批准引用 | 批准版本、哈希、任命、交付约定与授权 | 只批准明确快照；陈旧批准不能启动新输入 |
| 节点 | ID、依赖、截止时间、交付标准、相关执行及审核单元 | 节点结果由实际尝试、成果和审核推导，不另建一份可随意改的完成百分比 |
| 主动推进 | 下一检查时间、等待对象、依据、到期事件和处理结果 | 持久化在同一项目；重启可恢复；不创建第二套进度表 |
| 交付与操作 | 负责人交付说明、验收记录、改派与人工启动请求 | 实际文件仍以现有 delivery 快照为准，操作主体可追溯 |

继续以 `run.status` 表示唯一业务状态。新项目扩展草稿/规划、待方案批准、执行、审核、待实际文件、待最终验收、受阻、完成等必要状态；暂停和归档沿用现有控制字段。方案内部的征询与定稿是规划子状态，不另造一套与业务状态竞争的完成标记。`executionAttempts.state` 继续表示一次实际调用的事实，不能和项目完成混用。

现有 `run.items` 承接具体工作单元，增加节点引用及用途；新流程不再假定数组只有固定四项。规划、方案意见、负责人检查、执行与审核使用明确用途，以便共享并发和预算治理。计划批准快照、任命修订和当前指令纳入有效输入校验。

写操作采用预期修订、控制代数、输入哈希及幂等键。异步处理前和提交前都重新校验。方案意见同时返回、节点检查与成员结果同时到达时，按当前版本合并，不用旧的整份项目对象覆盖新反馈。角色变更和受影响的未执行单元在同一业务命令内更新；已有有效尝试先处理旧归属。

## 9. Grok Bot 接入方案与成立条件

目标是接入截图中的现用 Grok Bot Windows 应用，使用既有账号和获准会话。不能默认替换为 xAI 付费 API，也不能要求董事长逐次去该应用粘贴任务或取回结果。

当前可证实的是应用进程和版本；未验证后台收发、稳定目标 ID、长结果读取、文件读取和停止证据。已有 grok-bot-control 技能描述的是宿主能力约束，安装技能不提供应用、登录、MCP 或长期执行器。其可选 CLI 验证范围为 macOS Grok Bot 0.44.0、指定 app bundle 与 Node 22，不能直接外推至当前 Windows 1.2.3.0。

### 9.1 首阶段可行性核验

1. 查清当前 Windows 应用实际支持的官方桥接/扩展或可调用通道；若使用宿主 UI 工具，验证后台服务怎样合法、持续调用该能力。不能把本次 Codex 会话可用的 CUA 工具当作 Node 服务天然拥有的接口。
2. 在授权的隔离测试会话验证目标、输入框、完整待发内容、一次发送和新发出消息读回；不按侧栏位置猜会话、不覆盖无关草稿。
3. 用无业务内容的唯一测试标记验证完整返回、重复请求、超时、应用未启动、焦点变化和目标切换。未确认发送时进入不确定状态，不能换个通道再发一次。
4. 验证方案长度、中文、结构化返回，以及该角色所需材料访问。只会聊天不能标成可以完成本地文件独立审核；不具备文件权限时不得授予该角色能力。
5. 确定能由本机实际调度的薄适配器及停止/取消证据，然后接入现有执行治理；不另建平行项目台账或长期调度服务。

会话投递去重若确需本地传输日志，只保存目标引用、操作 ID、消息摘要、发送/读回状态和必要基线；它不是第二份业务进度表，不存登录凭据、原始私聊或重复项目正文。发送不确定时，CLI 与 UI 路径都不能自动重发。

### 9.2 可行性结果如何影响计划

可调用、可验证的通道通过后，才实施 Grok 实际派发并按角色逐项开放。若只能读、不能可靠发送或取回结果，成员显示“未验证/暂不可自动执行”，不得成为启动项目所依赖的可用成员。

负责人可以用已经获准且可用的成员继续其他实施与试点；这不代表 Grok 已完成。若没有可行通道，交付明确的技术阻塞证据和最小缺项，Grok 验收保持未完成。本计划不把“人工转发模式”作为满足董事长无需逐个追问要求的最终交付。新增软件安装、付费路线或对未审查私有协议的依赖，必须另行明确，不能默认进入本期。

## 10. 项目界面与全工作台精简

### 10.1 新建和方案页

新建页保留目标、交付形式、约束材料与三角色指定；业务项目关联可选。明确区分保存草稿、组织方案和正式启动。v2 组织选项保留为进阶能力，不把流程版本暴露为用户必须选择的术语。

方案页按初稿、执行人意见、审核人意见、负责人最终方案呈现，优先展示最终方案与阶段节点，原意见展开可查。批准按钮显示本次批准的版本、成果与节点，不能批准已过期草稿。

### 10.2 详情的三个部分

- 进展：负责人、当前节点、等待对象、持续时间、下一检查点、已完成节点和真实堵点；默认由负责人组织反馈，原始回执可展开。
- 成果：节点和最终成果、实际路径/版本、独立审核、查看或打开入口及最终验收。正文与附后未决事项分开。
- 讨论：保留指定成员及全员分别回复；讨论本身不启动阶段、不批准写作、不解除暂停。

同一状态只由一个投影生成。集中控制区保留启动、暂停、恢复、重试、改派、人工回填、旧执行核对、技能绑定、交付配置/生成/复核、归档与删除等已存在功能；按状态突出一个主要动作，其余在同一操作区或详情中可找回。提供旧入口到新入口的对应清单，防止“合并界面”实际变成删能力。

项目列表仍区分业务项目和协作任务，保留置顶、进行中、已完成和归档。列表优先呈现负责人、当前节点、等待时长、最近阶段成果和下一动作，点击进入原记录。

### 10.3 其他模块的范围

今日只汇总同源项目行动和待办，不复制项目进度。思考、行程复盘、论文、技能及报告继续保留原职责和数据边界。知识/报告细分优化后移；本期只处理确有重复的项目关联跳转、文案和投影，不借机重做其他模块。四主题、密度、装饰图、中英文和窄屏继续可用。

## 11. 历史兼容、上线和回滚

### 11.1 新旧流程隔离

新项目默认采用确认后的流程，旧项目继续识别原四岗位与组织版本，原记录和状态不改写。旧秘书成果作为历史成果可查，不伪造为新负责人的新交付，也不为了取消岗位删除历史文件。

明确转换旧项目时先只读预览影响、三角色和方案引用，核对有效调用已停止/归属已处理后才转换。转换保持暂停，不自动补跑、不清空原预算、不生成一条新链来绕过旧限制。归档、返工、文件核验失效、旧审核和迟到结果的事实全部保留。

### 11.2 部署顺序

开发继续保持 main 单一主线，不恢复 V8/V9 长期分支。按里程碑形成小提交，在隔离台账完成检查后再推进源码；业务数据、会话内容、成果文件和凭据不进入 GitHub。源码提交与真实业务验收分别记录。

首次启用采用显式新项目试点。部署前确认服务拥有的实际根目录、当前调用和待核对状态；有可能仍在运行的成员先处理，不强行结束未知业务会话。重启后比较项目 ID、归档/暂停、预算、正文哈希、文件引用及队列归属。WorkBuddy 定时领取开关和其他工具登录保持原授权状态，不因部署擅自启停。

### 11.3 回滚和备份

源码通过 main 历史回退或 revert；禁止强推删除已经发布的历史。改动前仅备份本次修改的文件，验证与提交后按已批准策略处理临时副本。唯一台账保持现有最近 3 份及最近 7 天每日快照策略；旧备份被自动审批拦截的手工清理不混入本期功能开发。

新字段采用增量兼容。回滚后的代码遇到新流程项目时保持只读或安全暂停，不把它当旧四岗位项目自动运行。需要还原台账时先核对还原点之后的新业务写入，不能直接覆盖较新的真实成果。新成果文件保持可定位，不因代码回滚删除。

## 13. 测试与最终验收矩阵

### 13.1 自动测试重点

| 编号 | 必须验证的行为 | 验证方法 |
|---|---|---|
| A01 | 三角色明确任命，能力不符不得偷换成员 | 领域/API 角色矩阵；缺配置、短测通过但角色未验证的反例 |

### 13.2 真实试点

用公开或虚构材料创建一个正文任务和一个实际 Word 文件任务。董事长在工作台指定三个可用成员；负责人真实拟方案、收意见、定稿；董事长批准；负责人按节点主动推进并交付，独立审核人读取实际材料和文件；董事长只在工作台对负责人验收。

至少覆盖一次安全的成员无法启动情景、一次审核退回、一次文件版本变化、一次暂停后迟到结果和一次服务重启。测试不要求真实破坏账号或服务，可用受控适配器故障结合独立的真实通道短任务验证。Grok 必须另有一次真实会话收发与被开放角色所需的材料能力证据，不能全部使用模拟器代替。

业务验收观察：普通推进问题要求董事长排障次数为 0；重复派发为 0；草稿丢失为 0；无文件假完成为 0；无授权自动重跑为 0；已批准节点均有成果或真实未达成回报。点击减少、等待缩短和模型调用量用改造前后同类任务实测，不预先编造节省比例。
