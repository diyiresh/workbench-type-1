## 编制定位

- 读者：工作台日常使用者，采用中文、操作路径和具体例子，不以接口参数为主要内容。
- 目标：知道每个入口负责什么、怎样完成常见工作、哪些动作会调用成员、如何判断成果真正交付。
- 形式：一份可独立阅读的 Markdown 手册，拟保存为 `docs/工作台使用说明-中文版.md`；不改变服务、业务数据或自动化状态。
- 事实基线：截至 2026-10-18 的当前实现。以现有代码与规范为据，标明未完成接入，不沿用已过时的 WorkBuddy 暂停说法。

## 调整后的内容结构

正文按“我现在要做什么”组织，每个场景统一写明：从哪里进入 → 操作步骤 → 何时需要确认 → 怎样判断完成 → 常见卡点。十个入口不再作为十个平行主章节。

### 开始使用前

- 如何启动和打开工作台；只有一份业务台账，其他页面引用同一事实。
- 区分查看／筛选、保存记录、调用成员和正式验收，先知道哪些点击会真正开始执行。
- 说明本文适用当前版本及尚未接入能力，不用演示记录冒充实际成果。

### 场景一：安排一天

1. **先看今天有什么**：工作首页看重点与风险；简报中心按今日／未读／来源筛选，阅读、标记已读及收藏。
2. **把事情放进时间里**：每日行程的日／周／月视图，新增或修改事项、类别、标签、材料路径和重点提醒。
3. **会前取得建议**：填写事项后点击建议，核对既往有效复盘的日期、原文和来源；用户决定采纳，不自动改写安排。
4. **执行与调整**：查看待处理／已完成／重点筛选；需要时修改安排、打开材料，说明学习和生活事项如何进入相应记录。
5. **当天收尾**：登记真实完成、写下复盘；周期报告在工作报告中生成、编辑和保存。复盘转为经验的后续操作进入场景三。

### 场景二：推进项目

1. **先选择正确入口**：业务项目跟踪长期任务，协作任务运行四岗位链；普通指令与群聊分别用于安排和讨论。
2. **提交一次清楚的目标**：目标、材料、约束、成员、交付物与验收要求；明确正文还是实际文件，正式写作仍需批准。
3. **看懂谁在做什么**：主管 → 执行 → 独立复核 → 整合；成员中心的登记状态、通道证据与真实执行尝试分别代表什么。
4. **与成员讨论和追踪**：项目群聊选择成员／@成员，Enter 换行、Alt+Enter 发送；四行说明、退回意见和执行记录按需展开。
5. **处理等待与异常**：WorkBuddy 自动领取的现有条件；外部定时开关与项目暂停的区别；失败、超时和迟到结果先核对再明确重试。
6. **拿到并验收成果**：文件生成、路径／版本／哈希、打开与独立复核；解释“内容通过”与“文件已交付”的区别。
7. **阶段结束后整理**：项目菜单、归档预览、恢复后明确继续；历史记录保留，归档不等于完成。

### 场景三：沉淀经验

1. **从一次具体经历开始**：行程复盘、项目成果、记忆或教训，区分业务事实、个人判断和待确认事项。
2. **把复盘整理成笔记**：生成可编辑摘要，补充待确认问题后先点击整合、核对预览，再确认保存 Markdown；保存本身不重新归纳。
3. **管理变化中的经验**：Obsidian 专用目录、最高有效版本、历史／停用状态、旧版预览和可恢复移除；解释下次建议到底读取哪一版。
4. **把稳定做法变成技能**：选择经验来源 → 编辑并保存草稿 → 确认发布 → 版本比较／回退草稿 → 固定输入测试 → 人工评价。
5. **让项目明确采用技能**：绑定已发布的具体版本与成员授权；区分“允许使用、已接收、实际采用”，不自动改成员全局规则。
6. **分清笔记与知识检索**：独立复盘排除 VaultRAG；普通资料检索保留来源，资料过时需要用户判断。当前知识可视化与第三方运行时接入的范围如实标注。

## 必须讲清楚的规则

- 不要求用户每次手动复制提示词；解释实际自动领取需要哪些现有条件，但不保证桌面每次都会成功。
- WorkBuddy 启停遵从用户当前选择；工作台不因刷新或恢复某个项目擅自改变外部定时任务。
- 项目群聊、正式执行、内容复核和文件验收分开。
- 复盘笔记独立于 VaultRAG，同一行程最高有效版本参与建议；保存本身不会自动整合回复。
- 技能候选需确认发布，测试需明确点击，不自动安装全局技能，不宣称其他成员测试已接通。
- 归档不是完成，恢复不是自动继续；不确定结果先核对，不能一直点击重试。
