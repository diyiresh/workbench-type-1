## 1. 平台定位、职责与能力边界

### 1.1 目标与当前状态

平台的目标是成为一个为用户工作的部门：用户提交目标，主管拆解与协调，执行人完成工作，复核人检查质量，最后给出可使用的交付物。

目前已经具备统一台账、固定工作链、项目消息流、成果对象、模型文字产出、真实 Codex 调用、进展记录和简报接收。跨软件自动派工、自动取回文件、持续自动监督尚未完成。现在仍需要点击启动 Codex；WorkBuddy、豆包的真实成果仍通过人工或外部 Agent 写回。

### 1.2 职责约定

| 成员 | 用户确定的职责 | 当前操作方式 |
|---|---|---|
| 用户 | 提出目标、人工脱敏、处理关键取舍 | 在页面提交目标和约束，提供脱敏正文；批准必要的外发等动作 |
| Codex | 项目主管、任务拆解、成果判断和返工意见 | 独立总管通道，支持主管与独立复核阶段 |
| WorkBuddy | 项目、任务执行 | 尚未接通自动派工；外部执行后回填真实成果 |
| 豆包及其他 Agent | 按能力承担具体工作 | 收件、打卡与回填需由成员实际执行；名称在册不代表软件已连接 |
| 本地 Ollama | 基础汇总、成果整理、进度对齐 | 通过普通模型路由调用；不负责保密原件处理 |
| 工作台 | 唯一台账、流程依赖、结果保存与展示 | 本机 Node.js 服务和浏览器页面 |

这些职责是运行约定，当前四阶段的默认承办人仍由代码按优先列表选择，不能保证新建时就显示上述分工。点击 Codex 拆解或复核后，对应阶段才会记录承办人为 `codex`、引擎为 `codex-chatgpt`。

### 1.3 三件容易混淆的事

- **下达不等于唤醒软件。** 底部指令台写入收件箱，接收方需要读取、回执和执行。
- **模型完成不等于项目完成。** 模型写出文本只是一个阶段成果；项目要经过执行、独立复核及整合。
- **登记路径不等于共享文件内容。** 台账保存位置，文件仍留在原目录；当前 Codex 通道不自动读取这些文件。

### 1.4 Ben_My_Agent 共享工作区

`D:\OneDrive\Desktop\Ben_My_Agent` 已登记为所有 Agent 的共享根目录。根目录下的 `skills`、`memory`、`context` 是共享层；每个独立项目继续保留在自己的子目录中，项目代码和项目材料不得直接混入共享层。平台通过 `GET /api/workspace` 提供机器可读的目录登记和发现结果，详细规则见根目录 [WORKSPACE.md](../../WORKSPACE.md) 及 [Agent接入邀请与项目协作协议](Agent接入邀请与项目协作协议.md)。

当前只完成目录和协议登记，原先分散在各 Agent 私有目录的 skills、memory、上下文没有自动搬迁。迁移必须逐项审核、去除保密内容后再放入共享层。

## 2. 安装条件、启动与关闭

### 2.1 本机条件

项目根目录：`D:\OneDrive\Desktop\Ben_My_Agent\5.cursor\搭建工作台`。

基础平台需要 Windows、可运行的 Node.js，以及浏览器。当前主程序使用 Node.js 内置模块，没有声明 npm 第三方运行依赖；启动不要求 Docker。Codex 总管另需本机 Codex CLI、ChatGPT 登录及可达的模型网络。Ollama 和微信提醒均为可选功能，分别依赖各自的服务与配置。

默认地址：`http://127.0.0.1:3780`。数据在根目录的 `data/store.json`。

### 2.2 推荐启动

1. 双击根目录 `start.bat`。
2. 浏览器打开工作台。若服务尚未就绪，等启动窗口显示服务地址后刷新。
3. 如果已存在健康的工作台，脚本只打开浏览器，不再启动第二个服务。
4. 此方式首次启动时，关闭服务窗口会停止服务；关闭浏览器本身不会停止服务。

脚本窗口显示的 v0.1 是旧版本文案，不能据此认定功能缺失。

后台启动可在项目目录执行：

```powershell
powershell.exe -NoProfile -File .\start-background.ps1
```

后台脚本隐藏服务窗口，检查健康状态，输出日志到 `logs`。它本身不建立开机自启或 Windows 服务；是否已有外部计划任务应另行核对。

开发者也可在项目目录执行：

```powershell
node server.js
```

### 2.3 健康检查与关闭

访问 `http://127.0.0.1:3780/api/health`，返回 `ok: true` 表示工作台 HTTP 服务可用，**不代表 Codex、Ollama、提醒通道均可用**。各通道应单独测试。

后台停止：先查监听3780端口的进程，核对其命令行确为本项目的 `node server.js`，再停止该进程。不要停止所有 Node.js 进程。正在运行的 Codex 任务会因服务停止失去正常回写机会；应尽量等任务结束再维护。

### 2.4 局域网模式

`start-lan.bat` 设置 `HOST=0.0.0.0`。同一网络设备可通过电脑的局域网 IPv4 地址访问。若本机服务已占用3780端口，必须先停止原服务才能换成该模式；防火墙仍可能阻止访问。

当前平台没有统一登录认证与按成员划分的权限体系，整份状态接口及 JSON 导出可能包含配置凭据。局域网模式会扩大访问范围，应保持默认本机模式，直到确有可信网络使用需求。部分接口还限制为本机调用，手机访问页面不代表能调用全部写接口。不要把当前服务直接发布到公网。

## 3. 页面功能与操作要求

页面采用三栏：左侧一级导航，中间模块或项目列表，右侧工作区；底部是指令台。左侧搜索用于筛选栏目，不是全文文件检索。

| 页面 | 用途与主要操作 | 输入与判断要求 |
|---|---|---|
| 指挥舱 | 查看概况、模块、风险及下一步；新增模块、拖动调整顺序 | 模块是展示入口；拖动排序不改变任务优先级 |
| 决策台 | 查看在办、受阻、逾期、未打卡；从会议记录拆待办 | AI拆解走普通模型；过目后再生成待办 |
| 虚拟部门 | 建立目标、查看四阶段、调用Codex、回填、复核及整合 | 输入明确目标、背景、截止时间、禁止事项和验收要求 |
| 每日行程 | 日/周/月查询、添加事项、完成、复盘、材料路径、报告草稿 | 行程日期与时间应准确；日程和项目任务分别存储 |
| 简报中心 | 查看外部简报原文、来源、时间与未读状态 | 简报由外部生产和报送，页面不自动替成员生成新闻 |
| 经营 | 从台账生成日报、复盘、周指导、周报、月评估、月报及季度总结 | 是台账汇总初稿，应检查事实和下一步 |
| 舰队 | 查看在册成员、下达指令、回执与同步信息 | 在线/在册标记不能作为外部软件正在工作的证明 |
| 事业部 | 按领域查看项目模块及任务 | 成果、责任与下一步应对应具体任务 |
| 学习 | 引用学习日程；生成、采纳、完成体系化学习计划 | 生成候选计划不等于已采纳；普通模型路由须可用 |
| 生活 | 引用生活日程；记录周期习惯 | 习惯记录不自动复制到每日行程 |
| 记忆 | 查看记忆、教训、技能及提示词资产 | 写可复用的规则与事实，不写未脱敏原件 |
| 设置 | 主题、JSON导出、Codex检测、模型路由、微信提醒 | 登录检测、配置保存与真实调用测试分别判断 |

### 3.1 决策台的待办拆解

1. 打开任务拆解，粘贴原始文字。
2. 可手写或点击AI拆解；AI使用普通模型路由，不是Codex总管通道。
3. 检查输出，每行采用 `任务标题 | 责任部门名称 | 一句话说明`。
4. 确认后生成待办，写入 `tasks[]`，初始状态为待启动。

该操作不会自动建立四阶段部门工作链，也不会自动发出执行指令。责任部门应匹配在册名称或ID，否则可能成为未分派。

### 3.2 底部指令台与舰队

选接收人、输入任务要求，再下达；页面可能先显示 Safe Mode 确认。选择全员会展开为各成员各一条收件记录，共享 `broadcastId`；每名成员应分别回执。

指令按 `queued → ack → doing → done` 推进。它与项目任务状态是不同记录：指令标完成后仍应给对应任务打卡。当前后台PATCH并未严格禁止跨阶段跳转，因此执行人必须主动遵守约定。

黄灯依据时间字段计算：任务在执行中或待核验、24小时无更新时提示；成员48小时无同步时提示。黄灯表示台账缺少新记录，不能证明软件卡住；“同步”时间更新也不能证明成果合格。

### 3.3 日程、提醒与报告

日视图添加事项，填写时间、标题、分类、标签、备注、材料路径；材料每行一条。周视图按周一至周日、月视图按自然月查询同一 `agendas[]`。完成后补复盘，避免只勾选而没有成果说明。

重点提醒需勾选重点、有有效日期时间、尚未完成、提醒通道已启用且凭据有效。服务每分钟检查；进入开始前12小时的窗口可发送，已过开始时间不会补发。发送成功记一次，失败间隔至少15分钟重试。若电脑或服务关闭，错过的提醒不保证补发；提示中的“约12小时后”也可能因晚启动而不准确，应以事项时间为准。

日程报告：在日/周/月视图生成相应日报/周报/月报草稿，读取该周期已录入日程与复盘，用普通模型润色；编辑并点击保存到报告库后才持久化。空周期无法生成。材料路径数量能参与底稿，文件正文不会自动参与。

经营页报告则由 `lib/report.js` 根据台账规则生成并直接写入报告库，不是每次都调用AI。两种报告不能互相当作完整工作事实。

### 3.4 学习与生活

“繁星”引用分类为学习/生活的日程，完成与复盘仍写回原日程；“银河”保存独立的习惯或学习计划。学习表单填写目标、内容、可投入时段、截止日期和单次时长，生成候选后核对再采纳。全部学习小节完成后，体系转为成就记录，具体小节被清除，应在完成前另行保存需要保留的细节。

生活默认习惯：每日9项；周一、三、五增加锻炼；周日增加拒绝清单和一种难事。同日期同习惯不重复创建。频率是默认方案，不代表用户必须全部完成。

## 4. 项目工作链的完整操作

### 4.1 创建目标

进入“虚拟部门”，提交目标与背景，建立工作链。初始只解锁主管，其余阶段等待前置成果。建议目标包含：用途、交付物、截止时间、可用材料、禁止事项和通过标准。

可参考以下示例，替换内容后提交：

> 目标：依据公开资料，形成某项目的研究初稿及来源清单。背景：用于内部讨论，限指定年份；所有输入已脱敏；不外发文件。验收：关键结论能追溯来源，缺失信息标待确认，最后由另一执行身份复核。

未提交的目标草稿保存在当前浏览器 localStorage，切换页面可保留；换浏览器、清理浏览器数据或换电脑不会自动迁移草稿。提交后才进入台账。

### 4.2 四阶段操作

| 阶段 | 正常操作 | 成功后 |
|---|---|---|
| 主管 | 点击“交给Codex总管拆解”；也可普通模型或真实成果回填 | 保存执行方案，解锁主执行人 |
| 执行 | 外部执行人完成任务，回填正文及材料位置；或选择普通模型文字产出 | 执行阶段完成，解锁独立复核 |
| 复核 | 点击Codex独立复核；或回填通过/退回及具体意见 | 通过解锁整合；退回使执行项进入返工 |
| 整合 | 回填最终交付或普通模型整合 | 四项全部完成后工作链为已完成 |

点击“人工 / 外部 Agent 回填”，非复核阶段填写成果和可选材料路径；复核阶段选结论并写意见；确认写入。要写真实正文、证据、缺口，不应只写“完成”。页面按阶段已有承办人记账，回填弹窗不提供实际作者选择；实际执行人与卡片不符时，应先由维护者修正责任身份，避免虚假归属。

### 4.3 返工与验收

复核意见应指出不符合哪条目标、缺少哪些依据及修改要求。返工时在执行阶段回填修订成果，原意见与历史讨论仍保留；新成果提交后重新复核，不能绕过直接整合。

状态含义：`blocked` 等待前置；`queued` 待启动；`doing` 执行中；`review` 待复核（可用状态）；`rework` 返工；`done` 阶段完成。工作链主要为 `planning / active / rework / completed`。普通项目 `tasks[]` 另用 `todo / doing / review / blocked / done / archive`，不可混为一个状态表。

独立复核以执行与复核的 `agentId` 不同进行校验。两个卡片名称不同并不保证使用不同底层模型，也不是专业第三方鉴证。

### 4.4 “一键自动接力”的范围

该按钮调用设置中的**普通模型路由**，最多推进8次文字阶段；不是启动Codex总管，更不是调用WorkBuddy或豆包软件。它可能仅完成文字推理，不能把建议文本当成文件加工、联网取证或软件操作已经完成。复核仍未通过时会停止，并保留进度。

有原件处理、实地事实核对、外部软件执行等任务，优先用主管拆解、真实执行、独立复核的分阶段方式。

## 5. Codex总管与普通模型路由

### 5.1 Codex连接测试

1. 本机Codex使用ChatGPT登录。
2. 打开设置，查看“Codex项目总管”检测结果。
3. 点击“测试Codex连接”，触发实际模型调用。
4. 等记录为已完成且输出“连接成功”。仅显示已登录不是网络、额度或模型可用的证明。

任务后台运行，可切换页面或关闭浏览器，但需要保持服务运行。页面在存在执行中任务时每3秒查询任务记录；历史失败记录保留，最新成功不要求删除旧记录。

### 5.2 主管拆解与复核

主管按钮只在主管阶段待启动时可用。复核按钮要求执行成果已提交、复核阶段待启动；若执行人为Codex，不能让Codex自审。成功输出自动写到阶段成果，无需再次回填；失败恢复为待启动，可重试。

同一运行中的工作链重复提交会返回已有后台任务。同项目正在由Codex处理时，阶段POST操作会被阻止。该保护不是所有接口的全局事务锁，维护期间不要通过整份台账覆盖接口并发改写。

当前调用输入为目标、背景、本阶段要求和已有阶段文字。不自动读取材料原件，不读取全部项目任务、私密文档或其他成员的聊天；拆出的子任务目前保存在方案文本中，不自动转为待办或执行指令。复核缺少文件正文时，应补已脱敏的内容或由实际具备文件访问能力的成员完成检查。

### 5.3 Codex技术与费用边界

调用为独立CLI进程，使用现有ChatGPT登录，不向该进程传入API Key。每次采用隔离临时目录、只读沙箱、临时会话和JSON事件输出；后台收到完整结束事件及非空文本才保存成功。CLI退出码须为0。默认调用计时上限为240秒，检测和代理查询还可能增加少量总耗时；输出超过200万字符会中止。

每次调用不是继续本聊天，也不依靠上次Codex会话自动记忆。任务记录虽然保存 `threadId`，当前并未用它恢复对话；项目连续性来自台账中的已有成果。CLI忽略个人运行配置，本工作台没有模型选择入口，实际模型取决于CLI默认行为和账号权限。

订阅调用受账户可用额度影响；程序没有自动切换付费API的逻辑。不要把“无需API Key”理解为无限调用。普通模型在线通道则可能按其服务商计费，须分别判断。

Windows已有进程代理时沿用；没有进程级HTTPS代理时读取已启用的系统代理，仅自动识别 `127.0.0.1:端口`，不修改系统设置。代理程序需实际运行。登录凭据由Codex维护，不能写入指南、台账或交接材料。

### 5.4 普通模型配置

设置页选择Ollama或OpenAI兼容在线接口，填写地址、模型、必要的API Key，勾选启用、保存，再测试。Ollama默认接口为 `http://127.0.0.1:11434`；Open WebUI管理页面不是该接口。在线地址需与服务商兼容 `/chat/completions`，当前实现不会自动发现模型能力。

普通路由用于决策台AI拆解、部门模型执行/自动接力、学习计划、日程报告润色等。设置成在线接口后，这些操作会把相应输入发送给所配置服务商。Codex总管是独立通道，修改普通路由不会切换总管。

Ollama只做基础汇总和进度整理是用户确定的分工，当前普通路由本身不按任务复杂度禁止调用，需要操作者遵守。模型输出不自动成为已验证事实。

## 6. 材料、成果与台账规则

### 6.1 人工脱敏与共享

保密原件由用户处理，先形成获准使用的脱敏副本，再提供给成员或粘贴到表单。证件、原件价格、未脱敏照片等红区信息不要报送。平台和Ollama都不承担自动脱敏保证。

原件、脱敏材料、成果建议放在明确分开的项目目录。只有成果位置登记到台账；需要让外部成员处理文件时，另外确认它实际可以访问该路径。路径登记不会改变文件权限、传输文件或提供全员同步。材料移走、改名后原登记可能失效，应更新位置。

### 6.2 材料打开与交付判断

每日行程的材料按钮由本机服务打开已登记且存在的路径，打开的是服务所在Windows电脑上的资源管理器，手机不会因此取得文件。部门卡片当前显示路径，不提供与日程相同的文件打开能力。

合格交付应包含：成果正文或文件、版本/日期、依据、未决问题、复核结论和下一步。`materials[]` 与 `artifacts[]` 是引用；文件备份必须另做，台账备份不会包含DOCX/PDF等原文件。

### 6.3 唯一台账

目标、阶段、复核、任务进度、报告与简报统一进入 `data/store.json`。不要在另一份表中独立维护相同项目进度。完成一段工作后更新已有任务的 `nextAction`，便于接班；完整简报需报送正文，聊天里显示不算入账。

页面导出的 `workbench-store.json` 是整份状态。普通模型API Key和提醒Token存于本地状态及备份，当前不加密；专用配置接口掩码不代表整份状态接口也已脱敏。导出、备份和整个项目目录均按敏感配置管理，分享前先剔除凭据。项目位于OneDrive目录，也不能仅因名字叫“本机台账”就认定未发生云同步。

## 7. 其他Agent接入与接口说明

### 7.1 通用约定

根地址 `http://127.0.0.1:3780`。JSON请求用 `Content-Type: application/json`，中文正文采用UTF-8程序序列化，避免手拼转义。示例中的占位ID必须替换成台账实际ID。

| 接口 | 作用及返回判断 |
|---|---|
| `GET /api/health` | 服务健康，不能代替模型测试 |
| `GET /api/state` | 读取完整台账，可能含凭据；勿直接转发 |
| `POST /api/checkpoint` | 更新既有任务，ID不存在返回404 |
| `POST /api/dispatch` | 写负责人、协作人及模式；不是软件唤醒 |
| `GET /api/inbox?agentId=codex&status=queued` | 查询该成员待领指令 |
| `PATCH /api/inbox/<id>` | 写回指令状态与回执 |
| `GET /api/departments` | 部门及工作链概览 |
| `POST /api/departments/runs` | 创建工作链，提交 `goal` 和可选 `context` |
| `GET /api/departments/runs/<runId>` | 获取某条工作链 |
| `POST /api/departments/runs/<runId>/items/<itemId>/action` | 开始、提交、返工、复核 |
| `POST /api/departments/runs/<runId>/items/<itemId>/model-execute` | 普通模型推进阶段 |
| `POST /api/departments/runs/<runId>/auto-run` | 普通模型最多8次接力 |
| `GET /api/codex/status` | 安装与ChatGPT登录检测 |
| `POST /api/codex/jobs` | 启动真实调用，返回202和 `job`，不是立即完成 |
| `GET /api/codex/jobs` | 返回 `{ jobs: [...] }`，看doing/done/failed |
| `GET /api/brief-runs` | 返回 `{ sources, runs }`，可按 `sourceId`、`unread` 筛选 |
| `POST /api/brief-runs` | 报送完整简报；以返回 `item` 与 `duplicate` 判断 |
| `GET /api/briefings` | 开屏简报集合 |
| `POST /api/reports/generate` | 按 `kind` 生成经营报告 |
| `GET /api/llm/config`、`GET /api/llm/status` | 普通模型配置与状态 |
| `PUT /api/llm/config` | 保存配置；现有项目说明有GET/POST概括，实际保存使用PUT |
| `POST /api/llm/test`、`POST /api/llm/generate` | 普通模型真实测试与生成 |

复核动作：`{ "action": "review", "reviewerAgentId": "实际复核人ID", "verdict": "pass或reject", "comment": "意见" }`。提交成果：`action: "submit"`、`output`、可选 `materials`。执行阶段返工用 `action: "rework"`。开始用 `action: "start"`；不要为了返工先把状态改成doing而失去返工语义。

Codex启动示例：

```json
{"runId":"替换为实际工作链ID","role":"director"}
```

连接测试用 `{"test":true}`，复核将 `role` 改为 `reviewer`。以 `job.status=done` 和实际输出为完成依据；202仅表示已受理。

### 7.2 指令执行与打卡

成员读取指令后依次PATCH：

```json
{"status":"ack"}
```

```json
{"status":"doing"}
```

```json
{"status":"done"}
```

然后给对应任务报送：

```json
{
  "taskId":"替换为实际任务ID",
  "agentId":"codex",
  "progress":45,
  "status":"doing",
  "nextAction":"根据复核意见补充来源清单",
  "notes":"已整理公开资料，尚未完成复核"
}
```

`progress` 是0—100的进度估计，不是质量分。`done` 应对应真实完成，仍待核验时使用 `review`。`collab` 模式为 `lead` 主控、`collab` 协作、`split` 分头、`lead-review` 主控加复核。下达 `POST /api/inbox` 为董事长界面入口，其他成员不得代替用户擅自向外发送指令。

### 7.3 简报报送

```json
{
  "sourceId":"chatgpt-daily-priority",
  "externalRunId":"2026-10-04-0800",
  "agentId":"chatgpt",
  "title":"每日优先事项简报",
  "completedAt":"2026-10-04T08:00:00+08:00",
  "body":"替换为完整简报正文"
}
```

首批来源还包括 `chatgpt-guangdong-construction`、`chatgpt-practical-ai`、`workbuddy-ai-news`。同一来源加同一 `externalRunId` 去重，不会用重复提交覆盖原正文；没有该ID时按正文等指纹判断。当前正文会清理首尾空白并限制20万字符，大型材料另行归档并标明边界。

成功后GET查询，找到相同来源和运行ID，核对保存正文与报送正文一致。不要把HTTP成功、页面摘要或源文件存在当作完整正文已入账的证明。外部简报的计划调度由原平台负责，工作台负责接收与显示。

### 7.4 文件报送

无法HTTP报送时，在 `data/dropbox/` 新建唯一名称的JSON文件；简报使用上面的字段并加 `"kind":"brief"`，进度则使用checkpoint字段。

服务启动约3秒首次扫描，之后每20秒扫描。成功移到 `processed/`，失败移到 `failed/` 并附错误说明。服务关闭时文件只能等待，不能宣称已收编。用程序写完整临时文件后再改为 `.json`，减少扫描到半写文件的概率。

当前进度文件通道与HTTP有差异：找不到 `taskId` 时会新建任务，而不是一定失败。因此务必先核对ID，否则拼错可能造出重复任务。`agentId` 缺失则失败。文件导入本身不会完成收件箱回执，也不会直接提交部门阶段成果。

### 7.5 其他维护接口

`POST /api/{tasks,specs,memories,lessons,reports,plans,events,skills,modules,inbox,prompts,agendas}` 为集合写入入口。以下对象支持按ID GET/PATCH/DELETE：`tasks/specs/memories/lessons/reports/plans/modules/inbox/agendas`。具体业务应优先用专用接口，以保留事件和校验；通用入口不是所有业务规则的保障。

日程材料：`POST /api/agendas/<id>/open-material`，提交 `index`。日程报告草稿：`POST /api/agenda/reports/draft`，提交 `view`、`anchorDate`。学习计划：`POST /api/learning/plans/draft`、`POST /api/learning/plans`；小节完成为 `PATCH /api/learning/plans/<planId>/sessions/<sessionId>`。习惯用 `GET /api/life/habits` 和 `PATCH /api/life/habits/<id>`。提醒配置用GET/PUT `/api/reminder/config`。主题用PATCH `/api/meta`，当前只允许 `theme`。

整份替换 `PUT /api/state`、重置 `POST /api/reset`、删除工作链和简报均属维护动作，不能作为日常打卡捷径。

### 8.3 持久化与后台

服务读JSON，在内存处理请求，写临时 `.tmp` 文件再重命名；失败时复制回主文件。多数写入同时生成备份，保留规则见第9章。迁移以补默认字段为主，修改迁移逻辑仍需先备份。

Codex后台任务在启动时先记doing，返回202；完成时重新读取最新台账再写结果。失败记录保留，阶段恢复queued。重启服务时，旧doing作业转failed，提示重新提交，不会自动续跑。后台不是操作系统持久任务队列；关机或进程崩溃不能保证自动完成。

本机任务、CLI事件和界面轮询构成一期连接；没有WebSocket项目群聊、其他成员实时消息桥或全员文件同步。当前JSON文件存储也没有数据库事务及统一多进程锁，只运行一个工作台写入服务，不直接并发改主文件。

## 9. 备份、恢复与故障处理

### 9.1 备份要求

设置“导出JSON”保存当前完整状态。写入自动备份位于 `data/backups/`，文件以 `store-` 开头、`.json`结尾，代码排序后最多保留12份；该规则也会包含人工命名且符合前缀的备份。自动备份保存的是本次写入后的状态，不应一概称为修改前快照。

重大维护前，另将当前台账复制到独立的、不会被该轮转规则删除的位置；成果文件也另外备份。不要把这类副本作为另一套运行台账。

### 9.2 恢复步骤

1. 停止本项目服务并确认无写入操作。
2. 保存当前 `store.json` 和需要调查的日志、投递失败文件。
3. 检查目标备份能被JSON解析，含必要的任务和工作链；不要输出其中凭据。
4. 将选定备份复制为 `data/store.json`。
5. 重新启动，核对健康、项目数、目标、成果和下一步。
6. 核对Codex中断作业、待处理dropbox及提醒状态。回滚可能恢复旧提醒发送状态、丢失新投递去重记录，需要防止重复动作。

当前页面没有一键恢复备份功能。重置不是恢复，整份状态PUT也不具备自动合并语义。

### 9.3 故障表

| 现象 | 检查与处理 |
|---|---|
| 页面打不开 | 先查health；确认Node服务、3780端口及启动日志，不先重置数据 |
| `EADDRINUSE` | 查端口所属进程，确认是否已有工作台；只保留一个实例 |
| Codex未安装/未登录 | 检测CLI路径和ChatGPT登录；不复制auth文件或凭据到台账 |
| 登录正常但测试失败 | 看job.error；检查网络、代理进程、额度及CLI兼容，重新做真实测试 |
| Codex超时 | 记录保留，阶段回待启动；缩小输入，补清楚要求后重试 |
| Codex长期执行中 | 确认服务仍运行；观察240秒调用上限；重启后中断项应标失败，不手工伪造done |
| 阶段未就绪/409 | 等前置完成；同项目Codex运行时不要再提交其他阶段动作 |
| 独立复核失败 | 执行与复核agentId相同，需另一实际复核人；不是改名绕过 |
| `fetch failed` | 通常对应普通模型通道；分别检测Ollama/在线接口，不误认为WorkBuddy失败 |
| 文件没有导入 | 服务需运行；查dropbox、processed、failed、错误说明和JSON编码 |
| 出现重复任务 | 检查文件通道taskId拼写；不要把未知ID当成新建许可 |
| 简报重复/正文没更新 | 同sourceId和externalRunId去重；新版本使用新运行ID并明确更正 |
| 文件按钮失败 | 检查已登记路径、索引及文件存在；它不下载远程文件 |
| 日程报告空/生成失败 | 查周期日程、普通模型启用与网络；未保存草稿不会在报告库出现 |
| 微信没有提醒 | 查重点、开始时间、done、sentAt、通道凭据与服务运行；已过开始不补发 |
| 进度和现实不符 | 核对updatedAt、实际文件及完成证据，更新nextAction；不要只改百分比 |

后台脚本日志为 `logs/workbench-startup.log`、`logs/workbench.stdout.log`、`logs/workbench.stderr.log`。Codex一期验收启动曾使用 `data/codex-server.*.log`，那不是所有启动方式的固定日志。当前CLI stderr不完整持久化，排查以job.error为入口，必要时由维护者做有控制的诊断。

## 10. 开发接续、测试及验收

### 10.1 开发流程

按用户工作区规则：完整系统开发先对齐需求、形成方案、调查GitHub可复用实现、确认技术/架构/MVP和顺序，收到 `Confirm Development` 后编码。完整文档在纲要确认及 `Start Writing` 后写作；本指南已获写作授权。

## 虚拟部门项目管理（2026年10月9日）

进入虚拟部门后，项目工作区提供“新建项目”，项目按置顶、进行中、已完成、已归档分组；桌面侧栏也提供相同分类。项目右侧“…”可置顶、取消置顶、重命名、归档、取消归档和删除。

归档保留项目、阶段成果、群聊及成果登记，不改变业务完成状态。删除前会弹出确认；删除仅移除工作台记录及关联消息、成果登记，不删除项目目录内的实际文件。重命名不改变原目标。

项目管理接口：PATCH /api/departments/runs/<runId>，支持 title、pinned、archived；DELETE 同一路径删除项目。管理接口仅允许本机调用。

### 项目启动故障修复（2026年10月9日）

原“一键自动接力”连续调用普通模型路由，不能代表 Codex、Cursor、WorkBuddy 真实执行。现改为“启动 Codex 总管”：通过 /api/departments/runs/<runId>/auto-run 启动真实 Codex director job；主管已完成时返回 waitingForAgent，不替外部成员生成阶段成果。各阶段普通模型推进按钮已移除。

项目明确指定的分工优先于默认分工。PATCH 项目接口新增 roleOwners，仅允许变更未启动阶段，并检查执行人与复核人不同。

资料库连接失败会显示具体服务地址。主管检索等待上限10秒，失败记录 evidenceWarning 和 blocker 后继续进行任务拆解，明确材料未核验；复核检索失败仍停止。后台任务结果以 /api/codex/jobs 的 done/failed 为准。
