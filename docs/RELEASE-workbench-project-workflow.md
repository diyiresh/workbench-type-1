3. 只读重新检查3780监听进程及其真实命令、健康状态、所有未完成作业与执行尝试。时间过去后不得沿用旧PID或“活动调用0”的旧结论。发现实际调用或不确定会话时先处理，不能盲目结束进程。
4. 在本机临时私有目录保存必要的比对快照：历史项目ID、暂停/归档/状态、预算、执行尝试状态与结果哈希、审核及文件快照、provider暂停选择；不把正文或凭据写进Git验证记录。
5. 按当前工作边界，暂不重启3780。需要部署时只结束已核实的本工作台进程，用原工作目录和Node入口启动，保持后台窗口隐藏；不另开第二个业务服务、不擅自启动WorkBuddy调度。

## 启动新版与现场初始化

- 使用现有 `npm start`（先构建资产）。核对实际新进程、启动时间、原工作目录、固定端口健康及对应静态文件。当前health不返回源码提交号，单独HTTP200不能证明后台已加载最新提交。
- 启动后的历史三条工作链应保持原暂停/归档/预算/成果；held记录不得自动解锁或误重派。发现差异时保留证据、停止试点，不直接覆盖旧台账。
- 用户本人在交互终端运行 `node scripts/chairman-auth.cjs setup`，两次输入不少于12字符的批准口令。不发送到聊天、不由实施Agent代设。不以鉴权测试中的公开假口令初始化现场。
- 未设置口令时明确阻止新流程的敏感操作，保持旧记录可读。现场初始化与测试环境的模拟批准是不同证据。

## 一次最小真实试点

新建一个公开虚构材料清单项目，交付一份Word、一个节点，不调用外网材料或真实业务文件。

材料：虚构条目A“整理材料”、B“核对证据”、C“形成清单”，各说明一句。方案须明确列出三项、注明材料虚构、不得声称已完成现实业务。执行输出保留这三项；审核逐条对应标准并引用实际读回内容。

三角色在试点项目里明确选择三名不同成员，不默认固定Codex负责，不把本轮开发分工继承到新项目。负责人先拟案，执行人与审核人给意见，负责人定稿；用户在工作台一次批准准确方案和节点。所选成员先完成真实角色探针；探针不发送业务材料，失败不得伪造通过或偷换通道。

批准后由既有通道执行、生成真实Word并独立审核，负责人整理交付说明。审核记录须绑定实际执行哈希和实际文件读回摘录；真实调用身份、时间、成果路径和哈希以唯一台账为准。用户在工作台对负责人最终验收，不代用户点击批准或验收。
